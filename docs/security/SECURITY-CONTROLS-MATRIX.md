# C-DAC Feedback Portal: Security Controls & Compliance Matrix

| Requirement / Standard | Category | Implemented Mechanism | Verification Evidence |
|---|---|---|---|
| **CERT-In Direction 2(a)** | NTP Synchronization | Target servers are named (`docs/security/INCIDENT-RESPONSE.md` §4: `samay1.nplindia.org`, `samay2.nplindia.org`, `time.nic.in`) and `DEPLOYMENT-CHECKLIST.md` has an unchecked "NTP synced" deploy-time check. **No systemd-timesyncd/chrony config ships in this repo** — this is a Target, not an implemented control. | `docs/security/INCIDENT-RESPONSE.md` §4 (server names only, not a working config). |
| **CERT-In Direction 2(b)** | 6-Hour Incident Notification | Formal incident notification procedure to `incident@cert-in.org.in` with emergency contact workflow, plus a named "Security Incident Owner" placeholder for CDAC to fill in before go-live. | Documented in `docs/security/INCIDENT-RESPONSE.md`. |
| **CERT-In Direction 2(e)** | 180-Day Audit Logging | `public.audit_logs` is append-only, DB-enforced by trigger (`trg_audit_logs_no_change`/`trg_audit_logs_no_truncate` block UPDATE/DELETE/TRUNCATE for every role including the table owner). A controlled retention script (`apps/api/src/db/retention-purge.ts`) is the one path allowed to age rows out past the 180-day floor (default 2 years), disabling/re-enabling the trigger inside one transaction. **Caveat:** nginx-layer rate-limit/CORS blocks aren't audited (only the application's own 403s are, via the shared error handler), and this is append-only, not cryptographically tamper-evident (no hash chain) — a Postgres superuser could still drop the trigger. Off-host: every encrypted DB backup (which includes `audit_logs`) and each day's container logs are copied, encrypted, to a network share with 180-day retention by `deploy/offsite-copy.sh`; container logs use the `journald` driver so redeploys no longer delete them. | Verified in `apps/api/src/db/migrations/002_security.sql:88-104` and `apps/api/src/db/retention-purge.ts`. There is no `schema.sql` in this repo (migrations are `001-005_*.sql`). `apps/api/src/modules/roster/service.ts` now logs the list of emails touched, masked (`st***@domain`) because the log cannot be edited for erasure requests, plus the count; report PDF/CSV downloads are audited as `REPORT_DOWNLOAD` (`apps/api/src/modules/reports/service.ts`); application authz failures (`AUTHZ_DENIED`) and bulk PII reads of `student_roster`/`staff_roster` (`BULK_READ`) are now audited too (`apps/api/src/app.ts`, `apps/api/src/modules/tables/service.ts`). |
| **DPDP Act 2023** | Notice & Consent | **Partially implemented.** The notice (`apps/web/src/app/auth.tsx`) now also writes a server-side record (`public.consent_records(email, version, accepted_at)` via `POST /api/consent`, migration `005_consent.sql`) alongside its `localStorage` flag, and staff (cc/admin) now get a one-time dismissible notice too — previously none did. Its text no longer contradicts the rest of the system: it now names Google OAuth's scope and the optional WhatsApp share instead of claiming zero third-party dependency. **Still open:** English-only, no notice-version history beyond the literal `'v1'` constant, no withdrawal/erasure path (see CMP-1). | `apps/api/src/modules/consent/service.ts`, `apps/api/src/db/migrations/005_consent.sql`, `apps/web/src/app/auth.tsx` — see CMP-4. |
| **DPDP Act 2023** | Grievance Contact | Admin-managed `public.grievance_officers(full_name, email)` (migration `004_grievance_officer.sql`), editable from Setup → Grievance Officer, visible to any staff, admin-only writes. **Still open:** this is a named contact, not a self-service access/correction/erasure endpoint for data principals — see CMP-1. | `apps/api/src/db/migrations/004_grievance_officer.sql`, `apps/web/src/features/admin/ManagePage.tsx`. |
| **Core Privacy Invariant** | Student Anonymity | `public.responses` table contains only `id`, `session_id`, `answers` (JSONB) — no user email, PRN, IP, or timestamp column. $k \ge 3$ response threshold + randomized ordering, enforced in `submit_feedback()`/`session_report()`. **Caveat:** not linkage-proof at the raw storage layer — `responses` and `submissions` rows from the same submission share `xmin`/heap order, and `submissions.submitted_at` sits next to them, so a DB superuser or decrypted backup holder could still correlate by position/time (CMP-3, target to fix: write `responses` in a separate, randomly-delayed transaction). | Enforced in `submit_feedback` & `session_report` in `apps/api/src/db/migrations/001_init.sql`. |
| **OWASP ASVS 2.1** | Session Management | Fastify signed cookies (`HttpOnly`, `SameSite=Lax`, `Secure`), 256-bit cryptographically random tokens, server-side revocation in `user_sessions`, and a live per-request roster re-check (`getSession` looks up the current role from the roster on every call — `apps/api/src/modules/auth/session.ts` — not a cached role, so removing someone from the roster revokes access on their very next request, no secret rotation needed). | Verified in `apps/api/src/modules/auth/session.ts` and `apps/api/tests/server.test.ts`. |
| **OWASP ASVS 4.1** | Access Control (BOLA/IDOR) | PostgreSQL Row Level Security (RLS) policies using the `app.current_user_email` GUC (via `my_email()`) preventing horizontal cross-centre/cross-course data leakage. | Verified across all tables in `apps/api/src/db/migrations/002_security.sql` and 11 tests in `apps/api/tests/rls-app-role.test.ts` (vitest, not pgTAP — there is no pgTAP suite or `schema.sql` in this repo; the "47 pgTAP tests" figure in earlier drafts of this document was left over from the retired Supabase version of this project). |
| **OWASP ASVS 5.1** | Injection Defenses | 100% parameterised SQL queries (`$1, $2, ...`), Zod schema validation on all inputs, CSV formula sanitization (`=, +, -, @`). | Verified in route handlers and `aggregate.ts`. |
| **OWASP ASVS 14.4** | HTTP Security Headers | Strict CSP (`default-src 'self'`; `style-src` needs `'unsafe-inline'` for recharts/react-pdf), HSTS (`max-age=63072000; includeSubDomains` — **no `preload` on any nginx-sent header**; only Fastify's own Helmet config sets `preload: true`, visible on proxied `/api/*`/`/auth/*` responses only), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`. `/healthz` and `/assets/*` intentionally send only HSTS + `nosniff` (CL-8, Low, not fixed in this pass). | Verified in `apps/api/tests/server.test.ts` and `deploy/nginx/nginx.conf`. |
| **Zero CDN Policy** | Supply Chain Security | Zero external runtime CDN dependencies (`unpkg`, Google Fonts, `cdnjs`) — confirmed, no third-party requests on any route. **Correction:** there is no `@fontsource/inter` dependency and no bundled font files at all; `apps/web/src/index.css` names `"Fira Sans"`, which the browser cannot find, so it silently falls back to the OS `system-ui` stack. Functionally harmless (no external request either way) but the stated mechanism was fictitious. | Verified by reading `package.json` and `index.html` (no font `<link>` or `@font-face`) and `src/index.css:9`. |
| **Data Resiliency** | Encrypted Disaster Recovery | Daily automated `pg_dump` with AES-256-CBC encryption plus an HMAC-SHA256 (encrypt-then-MAC, verified before decrypt), key via env var never on argv, 180-day local retention pruning, and a restore drill script. By default the dump runs as the Postgres superuser; an optional least-privilege `BACKUP_DB_ROLE` is documented (`deploy/.env.example`) but not mandatory, and the offsite copy needs its SSH key mounted manually — see `DEPLOYMENT-CHECKLIST.md`'s Accepted risk section. | Implemented in `deploy/backup/backup.sh` and `deploy/backup/restore-test.sh`; verified live. |
